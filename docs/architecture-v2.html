1 · System context

Who talks to Consentia

Consentia is not a system of record for customers — it is a system of record for decisions about customers. It references identities held elsewhere and owns consents, decisions and evidence.

3 · The two flows that matter

Check, and withdraw

If these two sequences are right, the product works. Everything else is convenience around them.

A · Processing check — the hot path, called before any use of personal data
Client system
POST /v1/consent/check { customer_ref, purpose, system, context }
Validation Engine
Resolve the purpose's legal basis from the register.
If legal_obligation → ALLOW without consulting consent state
→ Read model
Fetch derived state for (customer, purpose). Cache permitted, but see invariant INV-05.
Validation Engine
Evaluate: valid & unexpired → ALLOW · withdrawn, expired, absent, minor-blocked, or any error → BLOCK.
Timeout, exception or missing data all return BLOCK
→ Evidence Vault
Write the decision (inputs, outcome, reason, policy version) before the response returns.
Client system
Receives { decision, reason, policy_version, decision_id }
p50 ≤ 25 ms · p99 ≤ 100 ms
B · Withdrawal fan-out — the flow the whole demo builds toward
Preference Center
Customer toggles a purpose off.
Consent Repository
Append a withdrawal event. Nothing is updated or deleted.
INV-01 · append-only
Read model
Projection updated and caches invalidated — before the write is acknowledged.
A stale ALLOW after withdrawal is a severity-1 defect
Orchestration
Fan out idempotent commands to every subscribed connector. Legal-basis purposes are excluded from the fan-out.
Connectors
Each acknowledges, retries with backoff, or exhausts and lands in the dead-letter queue with an owner.
Never silently dropped
Evidence Vault
Dispatch, each acknowledgement, retries and DLQ entry all chained. Receipt issued to the customer.
This is the artefact a regulator asks for
Why at-least-once, not exactly-once: commands are idempotent by design, so a duplicate "stop marketing" is harmless. Chasing exactly-once here would add coordination cost for no compliance benefit.
4 · Architectural invariants

The decisions that must not be quietly reversed

These are not preferences. Each one exists because reversing it creates a compliance failure that is invisible until a regulator finds it. Changing any of them requires founder + counsel sign-off, not a pull request.

INV-01 · Append-only ledger
Never UPDATE or DELETE a consent row. State is derived from events. Without this, the audit trail is only as trustworthy as the last person with database access.
INV-02 · Fail closed
Every error path returns BLOCK. Timeouts, exceptions, missing data, degraded dependencies — all BLOCK. An engine that fails open under load is worse than no engine.
INV-03 · Purpose-bound
Every consent, check and decision names a customer, a purpose and a requesting system. No blanket consent exists anywhere in the model.
INV-04 · Audit before acknowledge
The evidence write completes before the action is reported as done. Not after, not asynchronously.
INV-05 · Cache invalidation precedes acknowledgement
A consent change is not acknowledged until every cache that could serve a stale ALLOW is invalidated. This is the single most likely source of a serious defect.
INV-06 · Reference, don't copy
Customer PII stays in the client's systems. Consentia holds references, consents, decisions and evidence — not a duplicate customer master.
INV-07 · Single-tenant, in-country
Deployed in the client's own environment. No shared data plane, no cross-client store, all data at rest in India.
INV-08 · Humans sign filings
The platform assembles regulator submissions; a named person reviews and signs. Nothing files autonomously.
How to enforce these in practice: make each one a test, not a wiki page. A fails-closed test on every decision path, a chain-verification test in CI, and a "stale ALLOW" integration test that withdraws consent and immediately re-checks. If the tests exist, the invariants survive team turnover.

What "good enough" means numerically

Validation latencyp50 ≤ 25 ms · p99 ≤ 100 msIt sits in the synchronous path of customer-facing transactions. Slower and teams will route around it.
Validation throughput2,000 checks/sec sustainedInitial rating for a mid-size retail bank. Scale horizontally — the service is stateless.

Chain verification≤ 60 s per 10 M entriesMust be runnable on demand during a regulator inquiry, not overnight.
Data residencyIndia, at rest and in transitClient contractual requirement and a procurement gate.
Open decision the team must not invent an answer to: what happens when Consentia itself is unavailable. Halting processing is safest and hurts the business; serving a cached last-known-good answer keeps the bank running and carries risk. Implement both behind configuration and let contract language pick the default — engineering must not decide this unilaterally.
Deployment topology (per client)
Client VPC / data centre
All services and stores. No egress of personal data.
Stateless tier
Gateway, Validation, Orchestration workers. Horizontally scaled, no sticky state.
Stateful tier

Ops plane
Metrics, tracing, DLQ depth, chain-verification job, alerting.
Single-tenant means a new client is a deployment, not a schema change. That is the point — and it is why multi-tenant hardening is a Phase-3 concern, not a day-one one.
6 · Build order

What to build first, and what can wait

The architecture implies a sequence. Build the spine deep before building anything wide — a thin version of all 21 modules impresses nobody and certifies nothing.

OrderComponentWhy here
1Event store + Consent RepositoryEverything derives from the ledger. Get append-only right before anything reads it.
2Evidence VaultBuilt alongside the ledger, not after — retrofitting an audit chain means re-writing history you cannot re-write.
3Validation EngineThe product's core promise. Harden with load and chaos tests before adding features.
4Connector Framework + one real connectorThe longest pole and biggest unknown. Start it in parallel with 3; do not defer it.
5Orchestration + DLQNeeds the connector contract to exist first.
6Preference Center + widgetThe customer-facing surface. High visibility, moderate effort, needs 1–3 working.
7Privacy Center, Drives, Health, GridRead models and workflows over existing primitives. Fast once the spine is solid.
8Governance modules, multi-tenant, certificationPost-pilot. Calendar-bound work that runs in parallel with everything above.
The milestone that matters is not a release date. It is the first time a withdrawal in Consentia blocks a real read in the client's real test system. Everything before that is preparation; everything after is refinement.
